## 2. 当前 V1.0.15 基线已经实现的能力

### 2.1 页面结构

1. **01 · 选择与播放视频：**本地视频上传、A/B 两组实拍样例。
2. **02 · 模型推理：**一次选择并运行一个模型；推理结果保存后供后续比较。
3. **03 · 分类结果：**显示 Top-5、类别分数和样例参考信息。
4. **04 · 主要人物连续行为分析：**显示人物检测框、框上方 Top-1 标签与概率；提供连续视频结果和动作时间轴。
5. **05 · 推理详情与实验记录：**查看诊断信息并导出 JSON。
6. **06 · 模型结果对比：**从已完成的模型结果中选择最多 3 个进行比较；勾选不会重新触发推理。

### 2.2 样例类别

**A类 · 日常行为（6类）**

- 挥手（Waving Hand）
- 用手机（Using Phone）：原“看手机”和“打电话”两个展示入口合并为一个行为；当前入口使用看手机实拍样例作为代表。模型提示词和模型本身未因此修改。
- 摔倒（Falling Down）
- 吃东西（Eating Food）
- 睡觉（Sleeping）
- 抽烟（Smoking）：Pexels 视频 14500436，作者 Wizarto Production，6 秒、3840×2160，通过 Pexels CDN 外链播放；不镜像视频文件，来源和许可信息保留在样例元数据中。

**B类 · 共同动作（6类）**

- 慢跑（Jogging）
- 瑜伽（Yoga）
- 俯卧撑（Push Up）
- 仰卧起坐（Situp）
- 芭蕾舞（Dancing Ballet）
- 呼啦圈（Hula Hooping）

样例目录来自 HF Dataset 的固定 commit。抽烟样例作为前端外链样例加入，不属于上述 HF Dataset commit 中的媒体文件。

### 2.3 当前模型与推理流程

- **MoViNet-A0/A1/A2：**Kinetics-600 视频动作分类模型；MoViNet 连续流式分析并生成时间轴。
- **Qualcomm VideoMAE：**Kinetics-400 模型，作为跨架构视频分类对照；按连续片段进行预测。
- **Apple MobileCLIP-S0/S2：**图像—文本语义匹配模型；按片段抽取人物关键帧进行匹配。它不是原生视频时序动作分类器，结果解释必须保留这一边界。
- **人物检测：**MediaPipe EfficientDet-Lite0 负责主要人物定位；现有流程跟踪主要人物，并将人物裁剪区域交给分类模型。
- **运行环境：**静态网页 + 浏览器端推理，模型权重按需下载；不依赖本项目自建 GPU 推理服务。

### 2.4 当前版本的边界

- V1.0.15 是浏览器端多模型实验和比较平台，不是自研视频行为识别模型。
- 当前样例主要用于打通流程和观察模型能力，均为 development-only；不能将其描述为正式 benchmark，也不能用单条样例结果宣称模型准确率。
- “用手机”是 UI 层的行为合并；没有修改 MobileCLIP 原有提示词，也没有训练新的分类器。
- “抽烟”已经加入样例选择器，但不代表现有模型已可靠掌握抽烟识别。
- 本次只发布已验收的演示基线，不将其他模型研究实验的失败检查误报为本次 UI/样例回归失败。V1.0.15 的关键浏览器回归和隔离 HF Static DEV 发布均已通过；其他实验性 E2E 检查仍需单独分析。

## 3. 下一阶段：Our Solution 自研系统

### 3.1 用户已经确认的总体思想

- 保留 V1.0.15 中所有第三方模型、模型选择方式、连续分析和结果对比功能，不破坏现有基线。
- 只新增一个独立的自研方案入口，界面名称为 **Our Solution**。
- 自研方案采用与现有模型不同的推理策略，并优先实现**不经过任何训练或微调**的方案。用户已确认以下模型复杂度递增原则：
  1. **第一优先：YOLO26s + 简单规则。**先验证 YOLO26s 是否能够完成目标行为所需的人物/物体检测，再用可解释的时空规则判断行为；能解决就不增加其他模型。
  2. **第二优先：增加一个现成姿态模型。**只有当简单规则确实需要人体关键点或姿态信息时，才接入一个已有姿态模型；不自行训练。
  3. **最后备选：K710。**只有前两级仍无法解决目标行为时，才进一步评估 K710 等更复杂方案。
- YOLO26s 的具体检测类别覆盖、手机/烟支等小目标可见性、遮挡和远距离条件下的可靠性，必须先做真实视频验证；不能仅凭模型名称推断其能够直接识别“用手机”或“抽烟”这类行为。
- 在主要人物框上方展示自研方案的英文动作标签及置信度；模型选项和结果对比中统一显示 **Our Solution**。
- 对外展示只突出 Our Solution 的能力，不在学生使用界面公开实现细节；内部研发文档则完整记录模型、数据、预处理、训练和评测过程。

### 3.2 优先解决的问题

重点研究两类细粒度日常行为的区分，并严格遵循“先规则、后加模型”的复杂度控制原则：

1. **Using Phone：**人物正在使用手机，包括看屏幕和手机通话等情形。
2. **Smoking：**人物正在吸烟，重点关注手部与口部动作、烟支及烟雾等可观察线索。

目标不是简单地把两个标签加入分类列表，而是通过连续时序证据，减少两类行为之间以及与其他相似动作之间的混淆。后续可扩展到 A 类其他行为。

### 3.3 下一轮应先完成方案设计，不直接改动现有基线

建议按以下顺序推进：

1. **明确任务定义：**确定 Using Phone、Smoking 的可观察判据、边界情况和不确定样例。
2. **零训练方案验证：**先验证 YOLO26s + 简单规则是否足够；只有证据表明需要关键点/姿态信息时，才加入一个现成姿态模型；前两级仍不够时再评估 K710。候选模型调研必须围绕这一顺序展开，不要一开始就堆叠多个模型。
3. **设计独立推理链路：**明确检测、跟踪、人物裁剪、时序采样、动作识别、平滑与置信度输出的接口。
4. **小规模真实样例验证：**先用少量人工核验视频验证端到端流程，不以一次性建设大规模数据集作为启动前提。
5. **量化比较：**至少报告每类 Precision、Recall、F1、混淆矩阵、误报/漏报、推理延迟、FPS、模型大小及 CPU/WebGPU/WASM 资源需求。
6. **DEV 集成：**确认方案可运行且结果可复现后，再增加 Our Solution 入口；原模型和原结果不得被覆盖。
7. **人工验收后发布：**沿用 DEV 预览 → 老师验收 → PR → main 的流程。

## 4. 开发约束与验收原则

- 新自研方案必须是独立模块，不能通过修改第三方模型标签或伪造分类分数来冒充自研模型。
- 原有 MoViNet、VideoMAE、MobileCLIP 及其模型权重、预处理、推理逻辑保持可回归。
- 新旧方案必须使用同一视频、同一主要人物区域和一致的评测样例，确保比较公平。
- 不能把模型 softmax/相似度分数直接称为准确率或经过校准的概率。
- 优先浏览器端真实推理，并优先零训练、零微调；如果 YOLO26s + 规则足够，就不增加姿态模型或 K710。
- 如果模型体积或算力要求使浏览器端不可行，应先比较可行替代路线并说明资源成本，不要直接引入复杂的登录或 GPU 配额流程。
- 不预先要求 120 条样例；先打通真实视频的端到端流程，再逐步扩充经过核验的数据集。
- 当前正式发布的 V1.0.15 是稳定基线。自研方案应从独立分支开发，例如 'feat/video-action-our-solution'，不得直接覆盖 main。
